# Canvas — 扩展接口：第三方固定组件

> [English version / 英文版本](EXTENDING.md)

状态：**未来扩展设计**，尚未交付插件加载器。本文记录 COMP-7 的
`PinnedNode` trait 已经遵循的约定，使第三方固定组件可以在 SHELL-5
（第一方固定组件：时钟、系统监视器）交付之后注册，而无需破坏 API。
不要把插件加载机制放进 COMP-7 本身；COMP-7 只交付一个内置 `PinnedNode`
（静态固定图片）来证明 trait 边界，这就是该里程碑的全部范围。

## 目标

让第三方能够添加一种新的画布固定组件（天气面板、待办列表，或任何拥有世界空间
位置和可渲染内容的对象），而无需修改 `nkdhr-canvas` 或 `nkdhr-ui` 本身。

## 为什么 COMP-7 的设计已经支持它

`PinnedNode`（见 `INTERNALS.md` 的 COMP-7 章节）特意采用最窄接口，
让节点能以与客户端窗口同等的方式加入画布渲染循环和输入分发：它只有身份、
世界空间矩形、显式层级、与渲染器无关的渲染数据，以及与后端无关的指针事件。
其中没有任何内容假定节点必须是第一方组件或由 `nkdhr-ui` 支持。
进程内 Rust trait 本身不承诺对独立编译代码提供 ABI；未来加载器必须把稳定边界
适配进这个注册表。

## 设计

从 COMP-7 开始，`canvas/world.rs` 内已经存在
`Vec<Box<dyn PinnedNode>>` 注册表（合成器自身的渲染循环正是借此把固定节点
与窗口一同迭代），这里不需要新增。未来扩展只是在它之上增加**加载**机制：

- 固定组件 manifest 格式：
  `~/.config/nkdhr/canvas-widgets/<name>/manifest.toml`，包含显示名称和共享库路径；
  共享库公开另行规定的稳定 `extern "C"` 边界。宿主适配器实现 Rust 的
  `PinnedNode`，共享库绝不跨 ABI 交换 Rust trait object 或 Smithay 渲染器类型。
- `nkdhr-settings`（SHELL-6）增加固定组件列表。每项都可开关，并能像第一方组件
  一样在画布上拖动放置；因为对画布渲染循环而言，两者没有区别。
- 放置使用 CTRL-5，但准确表示形式有意推迟到 SHELL-5/6 设计注册表 schema 时决定。
  目前的配置存储无法通过 `Set` 创建任意嵌套叶子；现在宣称使用
  `canvas.pinned-widgets.<name>.position` 会重复 COMP-4 为位置标记解决过的动态键问题。
  后续设计必须使用单个编码后的注册表叶子，或先通用地扩展 CTRL-5，再记录动态点路径。

## 第一版扩展不包含的内容

- 第三方组件代码沙箱（无 seccomp/namespace 隔离）。固定组件以合成器进程的完整权限
  运行。这比 CTRL-EXT 的自定义命令构成明显更大的信任边界：后者是普通子进程，
  而不是被载入接近特权图形进程的代码。SHELL-5 完成并真正开始这个扩展时，
  必须单独进行安全审查；本文明确记录，以免遗漏。
- 非 Rust 组件 SDK（如 WASM 或脚本语言绑定）。上面的 `extern "C"` 边界只是验证
  独立进程外编译可行的最小方案；更友好的开发体验属于建立在它之上的后续迭代。
